七、sql injection

sql注入是由于不安全的字符串拼接造成的

注入流程大致是：判断是否可注入，字符型还是数字型；猜解SQL查询语句中的字段数；确定显示的字段顺序；获取当前数据库；获取数据库中的表，字段名；下载数据

防御措施可以使用参数化查询和预编译语句(把结构和数据分开发送给数据库，数据库先编译好结构，再把用户输入的内容作为纯数据填入)；还有白名单，过滤掉特殊字符；最小权限原则(即使入侵成功，攻击者能做到事情有限)；隐藏错误信息，不把报错直接展示给用户；部署web防火墙(waf部署在前端，提前识别一些恶意请求)

八、sql injection(blind)

这东西叫sql盲注，就是程序存在sql注入漏洞，但是页面不会直接回显数据库查询的结果，也不会回显错误信息，我们只能通过页面行为的差异来判断

为啥会出现盲注呢，后端丢弃查询结果，只判断有无记录；开启自定义错误页，屏蔽数据库报错；只返回成功/失败这类的布尔状态；查询结果不渲染到前端

盲注分三大类：布尔盲注(构造条件，根据真假改变页面；页面内容/长度差异)；时间盲注(条件为真时触发延时函数；响应时间差异)；报错盲注(通过报错函数把数据带出；错误信息或者说是报错注入)

也就是说，我们在不停变换条件，把答案问出来

函数 作用
SUBSTRING(str, pos, len) 截取字符串（MySQL）
SUBSTR() / MID() 同上
ASCII() / ORD() 取字符 ASCII 码
LENGTH() 字符串长度
COUNT() 记录数
IF(cond, a, b) 条件判断
CASE WHEN ... THEN ... END 条件判断
SLEEP(n) 延时 n 秒（MySQL）
BENCHMARK(n, expr) 重复执行消耗时间
PG_SLEEP(n) PostgreSQL 延时
WAITFOR DELAY SQL Server 延时

布尔盲注：构造sql条件，条件为真，页面正常，反之异常。

通过这个判断是否有布尔型

时间盲注：页面无论真假都返回相同内容，无法用内容区分。此时让”条件为真”时数据库主动延时，通过响应时间判断。

手工盲注效率很低，建议sqlmap

十三、csp bypass

这个东西是绕过内容安全策防护的一系列技术手段，csp是旨在防御xss的浏览器安全机制，如果配置不当或有缺陷，仍然可以xss

csp是通过HTTP响应头告诉浏览器，哪些来源的脚本可以执行，那些不行，核心指令是script-src，用来限制js的加载，比如script-src 'self'，意思是只允许执行同源脚本，内联的就会被拦截

unsafe-inline：等于没开csp，内联脚本完全被允许，可以直接注入

或者你的csp信任了一些cdn，攻击者可以上传一些文件通过白名单引入执行

…

现在安全实践不再靠繁琐的白名单，而是推荐csp

  1. 使用 nonce 或 hash：只允许携带正确随机数或哈希的脚本执行。
  2. 配合 strict-dynamic：让被信任的脚本可以安全地加载依赖。
  3. 设置 object-src 'none' 和 base-uri 'none'：堵死插件和 base 标签劫持。
  4. 避免 'unsafe-inline' 和 'unsafe-eval'：这两个指令基本会让 CSP 形同虚设。
